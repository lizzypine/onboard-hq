# Persistent Review with Neon and dbmate

## Intent

Complete one saved onboarding workflow: anyone proposes a change from a synthetic update, a manager reviews each suggestion, and approved changes appear in the provider's checklist after a refresh or application restart. Preserve the original update, model output, and review result so users can explain how a status changed.

The project-wide spec is [the proposal](../../proposal.md), particularly **Saved Records**, **Human Review**, **Data Use**, and **Data Use > Incomplete Dates**. The existing live-extraction design describes the earlier slice; its temporary-state boundaries do not limit this new slice. This document proposes the implementation below for approval; no database changes are made by writing it.

## Decisions from the Conversation

- Anyone can propose an update; a manager approves changes.
- A simulated role is sufficient for now. Do not add sign-in or user accounts.
- Use the user's empty Onboard HQ Neon PostgreSQL database.
- Use dbmate SQL migrations to establish and evolve the schema.
- Read application connection settings from `DATABASE_URL` in the environment. It is already configured locally.
- Use Pydantic for validation, and require automated unit, integration, and end-to-end tests.
- Account for different provider types, including dentists and dental hygienists. Whether individual providers need checklist exceptions remains undecided.
- Allow for possible future local/cloud semantic routing using OpenCode at `opencode.ai`, confirmed as the tool the user meant by `opencode-ai`; its integration is outside this slice.

## Approaches

- **Saved review workflow:** Recommended in the conversation and taken forward when the user chose to add Neon. It completes the approval-to-checklist loop and retains history across restarts.
- **Temporary review workflow:** Considered as a smaller alternative, but it would discard decisions on refresh and defer the persistence the user now wants.
- **SQLite persistence:** Initially suggested as a simple local implementation; replaced by the user's explicit Neon PostgreSQL choice.

Within the chosen approach, the implementation proposal is direct parameterized SQL through Psycopg 3's async interface, with dbmate owning SQL migrations. An ORM would introduce a second mapping layer without replacing the SQL migration tool the user wants to try. Psycopg is a proposed technical call, not a library the user selected.

## Goals and Boundaries

Keep the existing single synthetic dentist and five checklist requirements as the initial fixture. Move their source of truth from the browser fixture into PostgreSQL, seeded by an explicit, repeatable development command. The schema must support additional provider types and separate their default templates from individual checklists. New provider/checklist administration and exception controls are outside this slice.

Persist the linked record types from the proposal, including provider-type and requirement-template definitions. Keep current extraction, requirement filtering, supporting text, warnings, and calendar inference. Review suggestions individually. Only a manager's approval, including approval with corrections, may mutate a checklist requirement. Show pending suggestions and completed review history after a refresh.

Do not add RAG, policy documents, email ingestion, uploads, reminders, real employee records, multi-provider message handling, a status taxonomy, or automatic readiness judgments. Keep the current date policy. A drug-screen appointment date is distinct from its deadline: applying a proposed date must never overwrite a deadline.

The simulated role is explicitly a demonstration control. A caller can select Manager mode; it does not prove identity. The server still checks the selected role on review requests so the prototype does not implement authorization solely by hiding buttons.

Future semantic routing may choose between local and cloud models using OpenCode (`opencode.ai`). Preserve the existing injectable model factory and validate all extraction output through the same Pydantic contracts, independent of provider. Do not add a router, new model credentials, an OpenCode dependency, or speculative routing infrastructure in this slice. The current OpenAI-compatible gateway remains the execution path. Investigate OpenCode's interfaces, the application's routing policy, and fallback behavior in a separate design; provider selection alone does not define semantic routing.

## Proposed Data Model

Use PostgreSQL UUID keys generated by the application, foreign keys, timezone-aware audit timestamps, and indexes on provider/update references and pending-history queries. No database extension is needed for identifiers.

| Table | Contents and relationships |
| --- | --- |
| `provider_types` | Stable type identifier and unique name, such as Dentist or Dental Hygienist. |
| `requirement_templates` | Provider-type FK and canonical requirement name, unique within that type. Defines checklist membership, not a provider's progress. |
| `providers` | Stable provider identifier, synthetic name, provider-type FK, and proposed start date. |
| `requirements` | Provider FK, optional source-template FK for provenance, snapshot of the canonical name, current status, deadline, separate nullable scheduled date, and integer version. Names are unique within a provider. |
| `updates` | Unique client request ID, provider FK, original message, snapshot of the provider context used for extraction, processing state, warnings or a safe failure category, and created/completed timestamps. |
| `suggestions` | Update and requirement references, proposed status/date, original supporting text, all existing date metadata, and the requirement version captured before model extraction. Preserve these values after review. |
| `review_decisions` | Unique suggestion FK, outcome (`approved`, `corrected`, or `rejected`), original and applied status/date values, simulated reviewer role, and review timestamp. No actual person is identified. |

Enforce that a suggestion's requirement belongs to the same provider as its update through database constraints as well as repository validation. Require nonblank original updates and statuses. Keep statuses as text, consistent with the current model; do not introduce a new approved vocabulary. Existing missing-date warnings remain visible.

One suggestion can receive at most one terminal decision. Pending means no decision row exists. `corrected` means a manager approved edited values; it is not a draft mutation of the model's original suggestion. Rejected suggestions retain their proposed values and never change the checklist. Store the actual before/after requirement values in the decision rather than treating model output as the previous state.

Application records are retained by default. Do not add deletion endpoints or cascade deletion of history. A seed command uses stable fixture IDs and initializes a new provider's checklist atomically without changing established checklists or history on subsequent runs. Seed data is separate from schema migrations and is not reapplied on every app start.

### Provider Types, Templates, and Individual Checklists

The proposed normalization adds `provider_types` and `requirement_templates` to the original five tables. When creating the synthetic fixture, select the dentist type's templates and create separate requirement instances for that provider. Template rows do not store individual statuses, appointment dates, deadlines, or review state. Do not infer any new deadline or initial-status policy from the template; the existing synthetic fixture supplies its known values.

Checklist instances retain their own names and progress. Editing a template does not propagate into existing checklists or rewrite their history. Restrict deletion of referenced types/templates so provenance is preserved. When assigning a source template, validate that its type matches the provider's type. Return the joined type name in the existing model context; extraction still uses only the provider's stored checklist, not every template for that type.

An optional source-template reference leaves room for a future individually defined requirement, but does not enable creating one in this slice. Do not add or remove checklist entries through the update-analysis or review endpoints. Whether exceptions are allowed, who can authorize them, and how their reasons are recorded remain open questions; this design does not invent a waiver or exception workflow.

Seed the existing dentist's templates and instance checklist using stable IDs. Do not invent a dental-hygienist checklist; only add additional type-specific fixtures once their requirements are validated. Test the type boundary with clearly synthetic test templates rather than asserting real licensing rules. Repeating the seed must not backfill newly added templates into a provider whose checklist already exists; initial checklist creation is a separate, atomic operation from inserting missing reference templates.

## Database Configuration and Migrations

The application uses `DATABASE_URL`. The configured URL is pooled. Add `DATABASE_URL_UNPOOLED` for dbmate, copied from Neon's direct connection option for the same database. Preserve the supplied TLS options; never print a URL, place a credential in a command-line argument, or send connection settings to the model/browser. `.env.example` contains placeholders only.

Keep numbered dbmate SQL migrations under `db/migrations/`, with `-- migrate:up` and `-- migrate:down` sections. Use `dbmate -e DATABASE_URL_UNPOOLED migrate` against the already-created Neon database. Do not use `up` to create a different database, do not run migrations implicitly on app startup, and do not use `drop` or rollback against the application database during verification. Commit a schema-only `db/schema.sql` dump generated with a compatible `pg_dump`; it contains no records or credentials.

Install a pinned dbmate release during implementation, record its version in setup/CI documentation, and use the same release for local checks and CI. Migrations are the schema authority; dbmate's `schema_migrations` records applied versions. Test `migrate` twice on an isolated test database to prove the second run has nothing pending. Exercise rollback and reapply only in that disposable test environment.

Use a bounded async Psycopg connection pool managed by the FastAPI lifespan. Open connections lazily enough that import and the HTML shell do not need a working database. Missing settings or a database/schema outage produce a safe, actionable 503 from data endpoints; there is no fallback to a browser fixture. Do not log connection strings or raw driver exceptions containing credentials. Parameterize all SQL. Release database connections before model calls and never hold a transaction open while waiting for extraction.

## Request and Review Flow

1. The page loads provider details and requirements from the server. It starts in Proposer mode and labels the control as a simulated role switch. Both roles may submit and view synthetic updates/history. Switching role does not save a review or change the checklist.
2. Analysis requests send the selected provider ID and original message, not a trusted browser-supplied checklist. The server fetches the provider and applicable requirements and captures their versions before calling the existing extraction pipeline.
3. Create an `updates` record in a short transaction before extraction, with a unique client request ID to prevent a retried submission from generating duplicate updates or model calls. Reusing the ID with a different provider or message returns 409. An already completed request returns its saved result; a currently processing request returns an explicit in-progress/conflict response rather than calling the model again. The original message and context snapshot remain unchanged.
4. Run model extraction outside a database transaction. Store all valid suggestions and warnings together with a completed processing state in one transaction. Unknown requirements remain warnings, not new requirements. Empty extraction is a saved completed update with insufficient information and no suggestions. Existing safe model errors mark the update failed without creating approval candidates; the user may submit a new request to retry. If the process stops mid-analysis, a `processing` update remains visible as unfinished and cannot be reviewed; no background recovery job is included.
5. The page lists pending suggestions with the original update, supporting text, proposed status/date, inference explanation, and warnings. Proposer mode has no review actions. Manager mode allows Approve, Approve with corrections, or Reject independently for each suggestion. A manager can edit a nonblank status and an optional date before approving. Date confirmation is part of the manager's approval form; editing invalidates any earlier confirmation. The original suggestion stays unchanged.
6. Send only a saved suggestion ID, review choice, edited fields if applicable, and explicit inferred-date confirmation to the review endpoint. The server loads the original suggestion and applies role, input, and concurrency checks. It never trusts client-supplied provider/requirement links, original values, or a client declaration that a suggestion is already approved.
7. Apply an approval and write its decision in the same database transaction. Lock/recheck the suggestion and requirement; compare the captured requirement version to its current version. A stale approval returns 409 with a request to reanalyze, without recording a decision or changing the requirement. Successful approval increments the version. Rejection may dismiss a stale suggestion because it changes no requirement, and still records a terminal decision.
8. A second review of an already reviewed suggestion returns 409 and the UI refreshes its saved state. Concurrent reviews produce exactly one decision. After success, reload the requirement and history from the server; do not make optimistic browser-only checklist changes.

Applying a suggestion with no proposed date preserves the requirement's existing scheduled date. The manager can explicitly select a clear-date action when correcting; omission and clearing are distinct. Deadline values remain unchanged. If an inferred date is kept or changed, approval requires a valid date and explicit manager confirmation; date confirmation alone never approves a status. A suggestion with an unresolved date can still have its status reviewed with the warning visible, consistent with current missing-date behavior. Fully specified dates remain explicit dates and do not acquire inference metadata.

## Interfaces and Responsibility Boundaries

Keep `GET /` as the HTML shell. Add read endpoints for providers, the selected checklist, and saved updates with suggestions/decisions. Keep `POST /updates/analyze` as the page's analysis operation but replace its browser-context request with provider ID, message, and request ID; return saved update/suggestion IDs alongside existing extraction information. Add a suggestion review endpoint using its saved ID. Unknown IDs return 404; invalid bodies/roles return 422; a well-formed Proposer review attempt returns 403; stale or duplicate operations return 409.

Tests may continue calling the pure extraction pipeline with `ProviderContext`. Only the transport request changes. No external API consumers exist in this prototype; update page and endpoint tests together rather than maintaining a second untrusted-context API.

Proposed modules, to be recorded in AGENTS.md when they actually exist:

- `app/main.py`: transport, dependency wiring, and error mapping.
- `app/page.py`: page markup/script if keeping the growing page in `main.py` would obscure routes.
- `app/models.py`: provider, persistence, and HTTP request/response contracts; keep model-specific extraction schemas in `app/agent.py`.
- `app/database.py`: environment configuration and async connection lifecycle.
- `app/repository.py`: parameterized SQL and transaction primitives, with no model calls or HTTP errors.
- `app/reviews.py`: saved update/review orchestration; extraction remains in `app/updates.py`.
- `app/rules/review.py`: pure role, decision, field, and stale-version checks; existing scope/date rules remain pure Python.
- `db/migrations/`: dbmate schema changes; a separate explicit development seed command loads only synthetic records.

These file names and driver choices are proposed builder calls. Split repository responsibilities further if needed; do not create a generic persistence framework. Use server-side data loading for approval and keep database types/SQL out of plain rules.

## Pydantic Validation

Continue using Pydantic for structured extraction and expand its explicit contracts to persistence and review. Validate request identifiers, simulated-role values, review choices, nonblank trimmed message/status fields, valid calendar dates, and correction/confirmation field combinations. Reject unknown fields in new write-request contracts so clients cannot supply server-owned approval state or provider links. Distinguish an omitted date from an explicit clear-date action. Use field-specific strict validation where coercion could change a review choice, identifier, or confirmation flag; do not apply a blanket strictness change to existing extraction models.

Validate repository records into typed application models and response contracts before exposing them to the page. Pydantic validates data shapes; plain Python review rules enforce role and business decisions, and SQL constraints/transactions enforce integrity and concurrency. Request validation errors return 422; valid Proposer requests to review remain 403. Invalid structured model output follows the existing safe model-error path and cannot become a saved approval candidate. No Pydantic model replaces server-side authorization checks or a database constraint.

## Verification and Completion

All automated model work uses `TestModel` with real model requests disabled, including the server process used by end-to-end tests. Add PostgreSQL integration coverage, not SQLite substitutes or mocks as proof of transactions. Use a separate `TEST_DATABASE_URL`; refuse to run integration setup against the configured application database, including the same Neon database through pooled versus direct hosts. Provision local disposable PostgreSQL for local tests and a PostgreSQL service in GitHub Actions. Missing test configuration must fail with setup instructions rather than skipping tests. Preserve existing rule/extraction contracts.

### Unit Tests

Use pytest for Pydantic validation, scope and date rules, simulated-role decisions, correction field combinations, date confirmation, and stale-version decisions without network or database access. Include malformed IDs/dates, invalid roles/outcomes, blank text, forged server-owned fields, and omission versus explicit date clearing. These tests establish deterministic data/business rules rather than model quality.

### Integration Tests

Exercise FastAPI endpoints, typed repository records, SQL constraints, migrations, and transaction behavior against real disposable PostgreSQL. Substitute only the model boundary with `TestModel`. Include persistence across fresh connections/app instances, seed idempotence, role enforcement at the HTTP boundary, rollback after failures, and duplicate/concurrent/stale review attempts. Check that rejected validation causes no partial writes.

### End-to-End Tests

Automate browser coverage using Playwright with pytest as the proposed browser tooling. Start the real FastAPI app against isolated test PostgreSQL and inject deterministic `TestModel` scenarios through a test-only server runner, not a production endpoint or a production model-switch setting. Disable real model requests in that server process and exclude application credentials from its environment. Migrate/seed the isolated database through the same tools used by the app.

Run the browser through propose, pending review, simulated role switching, manager approve/correct/reject, and checklist/history reload. Assert Proposer mode cannot apply changes, inferred-date confirmation resets after editing, stale/duplicate decisions display a recoverable result, and saved state survives both browser refresh and server restart. Include insufficient information, model/database failures, and safe text rendering. Manual inspection may supplement these tests, but cannot replace them.

Include all three layers in `uv run pytest` locally and in CI. Install the matching Playwright browser/runtime dependencies explicitly in setup and CI; missing browser or database setup must fail with instructions rather than silently omitting a test layer. Do not depend on live local/cloud models, Neon application data, or arbitrary waits to establish end-to-end success.

Verify:

- Fresh database migration, second migration as a no-op, schema dump, and rollback/reapply only on a disposable database.
- Idempotent seed retains reviewed statuses and history.
- Different provider types produce distinct initial checklists from synthetic templates; a mismatched source template is rejected, template changes leave existing instances unchanged, and repeated seeding does not backfill or overwrite an established checklist.
- Provider context comes from stored records rather than request forgery.
- Submitted updates and candidates survive a new connection/application instance without changing the checklist.
- Both simulated roles can propose; the server denies Proposer review attempts and permits Manager decisions.
- Approval, approval with corrected status/date, rejection, and explicit date clearing each retain the original evidence and produce the correct persisted result.
- Unsupported dates and missing reference dates keep existing warnings; inferred dates require manager confirmation; appointment dates never replace deadlines.
- Invalid edits, duplicate decisions, stale suggestions, and concurrent approvals cannot create a partial decision or silent overwrite.
- Empty extraction, model errors, database errors, and an unfinished analysis remain visible and distinguishable without exposing secrets or inventing success.
- Browser refresh/restart retains saved checklist, pending suggestions, and history. Exercise keyboard controls, narrow layouts, safe rendering of synthetic HTML-like excerpts, and Manager/Proposer switching with deterministic model output.

Run Ruff, mypy, and the complete pytest suite locally and in CI. Verify a forward migration and seeded/read-back data on the user's empty Neon database during implementation after the design is approved; use no real-model call for this check and perform no destructive migration test there. Open a PR with a Summary citing the affected proposal sections and a Test plan, maintain the PR-diagram skill's applicable output, and watch GitHub checks. The user merges.
